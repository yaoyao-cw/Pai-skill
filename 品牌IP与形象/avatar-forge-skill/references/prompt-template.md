# Fixed generation payload

Use this exact section order for every generation and edit. Do not remove headings. Materialize values; do not leave placeholders or references such as `COMMON` in the payload.

## Preflight assembly

1. Resolve one complete Style Contract from `style-packs.md`.
2. Replace any user-overridden field; remove the superseded value.
3. Expand the full common and pack-specific negative lists.
4. Serialize the complete `[STYLE CONTRACT — LOCKED]` block once and copy it verbatim to every call in the batch.
5. Assign only the candidate-specific values permitted by `allowed_variation`.
6. Check coverage, fingerprint count, locked-field divergence, and variation budget.

## Editing template rule

For a same-pack edit, keep the same template. Put the approved pack-native source in its reference field, describe only the requested change in `Requested delta`, and repeat unchanged properties in the continuity lock. Do not shorten the Style Contract because the model previously saw it.

For a pack change, do not edit or attach the previous pack's generated avatar. Start a new generation, reuse only the original identity source plus text anchors, and set `Pack-native reference(s): none` until the new pack has an approved pilot.

## Negative-prompt routing

- **Single-prompt or modern instruction-following tool:** include the full hard-negative block in the main prompt.
- **Documented dedicated `negative_prompt` field:** keep the two concise “Do not” sentences in the main prompt and mirror the expanded comma-separated list into the dedicated field.
- **Unknown capability:** use the single-prompt route. Do not guess unsupported parameters.

Record `constraint_delivery_mode` as `main-prompt` or `main-plus-dedicated-negative` in the batch report.

## Batch invariants

The following substrings must be byte-for-byte identical across every prompt in one batch:

- the entire `[STYLE CONTRACT — LOCKED]` block;
- the style part of `[CONTINUITY LOCK]`;
- the complete `[HARD NEGATIVE CONSTRAINTS]` block.

Only identity/content blocks and `[THIS CANDIDATE'S ALLOWED VARIATION]` may differ, and only within the contract. For diverse series and matching sets, identities and resolved background states may differ per file; the Style Contract and its background-resolution rule still must not differ.
